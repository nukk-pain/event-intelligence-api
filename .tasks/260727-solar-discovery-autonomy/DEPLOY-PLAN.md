# 배포 설계 — ingest 액션 보강

작성 2026-07-27. 구현 전 설계만 정리한 문서다. 아직 배포하지 않았다.

## 현재 프로덕션 조건

```
eventsintel-ingest.timer     OnUnitActiveSec=24h
EVENTSINTEL_INGEST_DEADLINE  20m
EVENTSINTEL_RATE_PER_MIN     30       (호스트당)
EVENTSINTEL_SOURCE_CONCURRENCY 2
EVENTSINTEL_DETAIL_WORKERS   4        (최대 8 동시)
Solar Private Beta           400 RPM / 150,000 TPM
```

보강 대상은 670건 중 액션 필드가 빈 약 550건이다.

## 비용 계산

한 건당 실측치는 `abbench-solar-open2-20260717.md`의 eventagent 값을 쓴다.
3콜, 1,258 입력 + 278 출력 토큰, 5.3초.

| 항목 | 550건 전체 |
|---|---:|
| Solar 콜 | ~1,650 |
| 토큰 | ~845,000 |
| 400 RPM 하한 | 4.1분 |
| 150k TPM 하한 | 5.6분 |
| 모델 시간 (8 동시) | ~6분 |
| **링크 fetch** | **~1,100회** |

### 정정 (2026-07-27)

이 문서의 최초 결론은 틀렸다. "링크 fetch가 소수 호스트에 몰려 30분을 넘는다"고
썼는데, 실제 `homepage_url` 분포를 재보니 **657건이 430개 고유 호스트에 흩어져
있다.** 최다 호스트도 39건이라 링크 fetch 78회, 30회/분 기준 2.6분이다. 행사마다
자기 도메인을 쓰기 때문이고, 벤더 사이트에 몰린다는 가정 자체가 근거 없었다.

**따라서 전체 550건 일괄 처리가 가능하다.**

| 제약 | 550건 전체 |
|---|---:|
| 링크 fetch (최다 호스트 39건) | 2.6분 — 병목 아님 |
| Solar 400 RPM | 4.1분 |
| **Solar 150,000 TPM** | **5.6분 — 진짜 병목** |
| 벽시계 (8 동시) | ~6분 |

기존 크롤 2~5분에 보강 6~10분을 더해도 20분 데드라인 안이다.

**새로 드러난 위험**: 8 동시 × 1,536토큰 ÷ 5.3초 ≈ 139k TPM으로 150k 상한에
거의 붙는다. 토큰 인지 페이싱이나 429 백오프가 없으면 레이트 리밋에 걸린다.
이것이 전체 커버 설계의 핵심 과제다.

## 설계

### 1. 전체 커버 — 한 실행에서 전부 처리한다

```
EVENTSINTEL_SOLAR_MAX_CALLS=600    # 550건 + 여유
```

병목은 150,000 TPM이다. 845,000토큰이므로 하한 5.6분이고, 8 동시로 벽시계 약
6분이다. 크롤과 합쳐 20분 데드라인 안이다.

**전제 조건은 토큰 페이싱이다.** 8 동시가 139k TPM으로 상한에 붙으므로, 페이싱
없이 예산만 올리면 429로 실패한다. §7 참조.

### 2. 재시도 방지 — 커버리지가 아니라 비용 문제

전체 커버에서는 커버리지 전진 문제가 사라진다. 남는 것은 비용이다. 채우지 못하는
이벤트를 매일 다시 시도하면 정상 상태에서도 매일 1,650콜을 태운다. 시도 상태를
저장하면 정상 상태 비용이 신규·변경분으로 줄어든다. 전체 커버의 차단 요소는
아니므로 우선순위는 낮다.

시도 상태를 저장해야 한다. 스키마 마이그레이션이 필요하다.

```sql
-- internal/store/migrations/0010_action_enrich_attempt.sql
ALTER TABLE events ADD COLUMN action_enriched_at TEXT;
ALTER TABLE events ADD COLUMN action_enrich_result TEXT;  -- filled|empty|error
```

선정 규칙:
- `action_enriched_at IS NULL`인 것을 먼저 (미시도)
- `result='empty'`는 공식 페이지 내용이 바뀌었을 때만 재시도
- `result='error'`는 3일 후 재시도
- `result='filled'`는 재시도하지 않음

### 3. 우선순위 — 예산이 모자랄 때의 안전망

전체 커버가 되면 순서는 결과에 영향이 없다. 다만 예산이 조기 소진되거나 데드라인에
잘릴 때 무엇이 남는지를 결정하므로 임박순을 유지한다. 지난 행사의 등록 마감은
가치가 없다.

### 4. 데드라인 상호작용

파이프라인은 소스·ref 사이에서 ctx를 확인하고 `Report.Truncated`를 세운다. 보강이
데드라인을 먹으면 **크롤 자체가 잘려 discovery floor가 오염될 수 있다.**

보강에 별도 하위 데드라인을 준다. 전체 데드라인의 절반을 넘지 않게 한다.

```
보강 예산 = min(SOLAR_MAX_CALLS, 남은 시간이 허용하는 건수)
```

크롤이 끝난 뒤 남은 시간으로 보강하는 순서가 안전하다. 현재는 상세 파싱 도중에
인라인으로 돈다. 이 순서 변경은 별도 작업이다.

### 5. 관측

기존 로그 한 줄로는 부족하다. 배포 후 다음을 확인할 수 있어야 한다.

```
solar enrichment: attempts=N filled=M empty=K error=E budget_exhausted=bool
                  elapsed=Xs venue_fetches=Y
```

`deploy/verify.sh`에 보강 로그 존재 확인을 추가한다.

### 7. 토큰 페이싱 — 전체 커버의 핵심 과제

150,000 TPM 상한에서 8 동시는 약 139k를 쓴다. 여유가 7%뿐이라 응답 길이가
조금만 길어져도 429가 난다. 셋 중 하나가 필요하다.

- **토큰 인지 리미터**: 요청 전 예상 토큰을 창(window)에 적립하고 초과하면 대기.
  `internal/fetch/limiter.go`의 호스트 리미터와 같은 패턴을 Solar 백엔드에 적용.
- **429 백오프**: `Retry-After`를 존중하는 재시도. 단순하지만 상한에 계속 부딪히면
  처리량이 들쭉날쭉해진다.
- **동시성 하향**: 보강 전용 세마포어를 6으로 두면 약 104k TPM으로 여유가 생긴다.
  가장 단순하고 벽시계는 6분에서 8분으로 늘 뿐이다.

세 번째를 기본으로 하고 429 백오프를 함께 넣는 것이 위험 대비 비용이 가장 낮다.
토큰 인지 리미터는 필요해지면 그때 넣는다.

### 6. 롤백

`EVENTSINTEL_SOLAR_ENRICH` 미설정이면 즉시 기존 결정적 동작이다. 코드 롤백 없이
환경변수만 지우고 유닛을 재시작하면 된다. 이미 그렇게 되어 있다.

## 배포 순서

1. 마이그레이션 `0010`과 시도 상태 기록 구현
2. 선정 쿼리(미시도 우선, 임박순, 지난 행사 제외) 구현
3. 보강을 크롤 이후 단계로 이동, 하위 데드라인 부여
4. 로그 확장과 `deploy/verify.sh` 체크 추가
5. 보강 전용 동시성 상한과 429 백오프 구현 (§7)
6. 로컬에서 `MAX_CALLS=600` 전량 리허설. 벽시계·TPM·429 발생 여부 측정
7. 프로덕션 1회 수동 실행 후 데드라인 여유와 로그 확인, 그다음 타이머에 맡김

6번을 건너뛰면 안 된다. TPM 상한 여유가 7%뿐이라 실측 없이 프로덕션에 올리면
429로 절반만 채운 채 끝날 수 있다.

## 하지 않기로 한 것

- 데드라인을 20분 이상으로 늘리기. 24시간 주기와 flock 단일 실행 보장을 지키려는
  값이다. 늘리면 크론이 겹칠 위험이 생긴다.
- 호스트당 30회/분 완화. 크롤링 예의 정책이고 벤더 차단 위험이 있다.
- 데이터 기반 없이 병목을 단정하기. 최초 결론이 그렇게 틀렸다. 호스트 분포를
  재보기 전까지 링크 fetch가 병목이라고 단정했다.
