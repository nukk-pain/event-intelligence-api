# Solar 보강 정확도 감사

결측을 채웠다는 숫자와 맞게 채웠다는 숫자는 다릅니다. 여기서 두 번째 숫자를
만듭니다.

동일 216건 스냅샷에서 대조 실행과 보강 실행을 비교했습니다. Solar가 새로
추가한 61개 값을 빠짐없이 뽑아 각 값의 근거를 그 행사의 공식 소스 페이지에서
직접 찾았습니다.

```sh
make eval-report        # summary.json 재생성
python3 eval/audit.py   # 전수 재감사 (소스 페이지 재수집, 수 분 소요)
```

## 결과 (2026-07-27)

| 필드 | 검증됨 | 전체 |
|---|---:|---:|
| `name_en` | 17 | 19 |
| `register_url` | 10 | 16 |
| `registration_deadline` | 1 | 10 |
| `exhibitor_deadline` | 2 | 16 |
| 합계 | **30** | **61** |

`verified`는 소스 페이지에서 값과 마감 맥락을 함께 확인한 값입니다.
`partial`은 값만 있고 맥락은 못 봤습니다. `unverified`는 읽은 페이지 어디에도
근거가 없었고, `wrong_type`은 반대 유형 마감일을 가져온 경우입니다. 마지막은
1건 발견됐습니다.

## 감사 뒤 바꾼 것

마감일 26건 중 근거 확인은 3건뿐이었습니다. 그래서

1. 이제 보강기는 에이전트가 실제로 읽은 페이지에 그 날짜가 문자 그대로
   존재할 때만 마감일을 저장합니다.
2. 마이그레이션 0010이 검증 도입 전에 저장된 Solar 마감일을 전부 무효화하고
   `missing_fields`로 되돌립니다. 다음 수집이 근거 있는 값만 다시 채웁니다.
3. 검증을 통과한 값에는 `eventsintel/solar-enrich/v2` publisher가 붙어 회수
   대상과 구분됩니다.

## 이 대조가 놓치는 것

자동 대조는 읽은 페이지에서 텍스트를 찾아보는 것뿐입니다. JS로 렌더링되는
값이나 감사가 훑지 않은 더 깊은 페이지의 근거는 놓칠 수 있습니다. `unverified`가
전부 오류는 아니고, `verified`도 날짜와 맥락이 맞았다는 뜻이지 사람이 전 건을
다시 읽지는 않았습니다. 저장 게이트는 감사보다 보수적입니다. 에이전트가 읽은
텍스트에 값이 실재할 때만 통과시킵니다.

## 재감사 (2026-07-29) — 프로덕션 마감값 전수

carry-forward 래칫 도입으로 잘못된 값의 유일한 제거 경로가 감사가 됐으므로,
프로덕션의 마감값 37건(24개 행사) 전수를 같은 도구로 재감사했습니다.

| 분류 | 건수 |
|---|---:|
| verified | 5 |
| partial | 5 |
| unverified | 25 |
| wrong_type | **2** |

unverified는 "감사기의 정적 fetch로 재확인 실패"이지 오류 확정이 아닙니다
(쓰기 시점에는 에이전트가 읽은 페이지의 문자 증거를 통과했고, 감사기는 JS
렌더링·심층 링크를 못 봅니다). wrong_type 2건은 확정 오류였습니다:
배터리코리아(참가비 잔금 기한 → 부스 마감으로 저장), 홈테이블데코페어(부스
조기신청 마감 → 참관 등록 마감으로 저장).

## 재감사 뒤 바꾼 것

1. 마이그레이션 0011이 wrong_type 2건을 무효화합니다.
2. 쓰기 게이트가 유형 문맥까지 검사합니다(typedDateEvidence): 날짜 주변
   ±120바이트에 마감 어휘 그리고 그 마감 유형의 문맥 어휘가 함께 있어야
   저장됩니다. 위 2건의 재유입은 구조적으로 차단됩니다.
3. ingest가 끝날 때마다 "deadline coverage: upcoming events with a deadline
   = N"을 로그로 남깁니다. 래칫 이후 이 수는 단조 증가해야 하므로, 감소가
   곧 회귀 알람입니다.
