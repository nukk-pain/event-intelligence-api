# Solar 보강 정확도 감사

결측을 채웠다는 숫자와 맞게 채웠다는 숫자는 다릅니다. 이 디렉터리는 두 번째
숫자를 만듭니다.

동일 216건 스냅샷에서 대조 실행과 보강 실행을 비교해 Solar가 새로 추가한 61개
값을 전수 추출하고, 각 값의 근거를 그 행사의 공식 소스 페이지에서 직접
찾았습니다.

```sh
make eval-report        # summary.json 재생성
python3 eval/audit.py   # 전수 재감사 (소스 페이지 재수집, 수 분 소요)
```

## 결과 (2026-07-27)

| 필드 | 검증됨 | 전체 |
|---|---:|---:|
| `name_en` | 17 | 19 |
| `register_url` | 10 | 16 |
| `registration_deadline` | 1 | 10 |
| `exhibitor_deadline` | 2 | 16 |
| 합계 | **30** | **61** |

분류 기준: `verified`는 소스 페이지에서 값과 마감 맥락을 함께 확인,
`partial`은 값은 있으나 맥락 미확인, `unverified`는 읽은 페이지 어디에도
근거 없음, `wrong_type`은 반대 유형 마감일을 가져온 경우(1건 발견).

## 이 감사가 낳은 조치

마감일 26건 중 근거 확인은 3건뿐이었습니다. 그래서

1. **저장 전 근거 검증**: 이제 보강기는 에이전트가 실제로 읽은 페이지에 그
   날짜가 문자 그대로 존재할 때만 마감일을 저장합니다.
2. **기존 값 회수**: 마이그레이션 0010이 검증 도입 전에 저장된 Solar 마감일을
   전부 무효화하고 `missing_fields`로 되돌립니다. 다음 수집이 근거 있는 값만
   다시 채웁니다.
3. **세대 구분 출처**: 검증을 통과한 값은 `eventsintel/solar-enrich/v2`
   publisher를 달아 회수 대상과 구분됩니다.

## 방법의 한계

자동 대조는 읽은 페이지의 텍스트 검색입니다. JS로 렌더링되는 값이나 감사가
읽지 않은 더 깊은 페이지의 근거는 놓칠 수 있어 `unverified`가 전부 오류라는
뜻은 아닙니다. 반대로 `verified`도 날짜와 맥락 일치까지이지 사람이 전 건을
읽은 것은 아닙니다. 그래서 저장 게이트는 감사보다 보수적으로, 에이전트가 읽은
텍스트에 값이 실재할 때만 통과시킵니다.
